# V3.7.0 Task Session Unified Contract Design

## Status and scope

This design implements only the remaining first-batch Task Session contract
from the approved V3.7.0 R3 design. It is a disabled public-component
foundation. It does not register or enable `assistant-work`, change Router or
Dispatcher behavior, create a draft workspace, search knowledge, generate
files, migrate production state, deploy, or restart the service.

The owner directed strict R3 execution, automatic implementation, no
subagents, no GitHub upload for now, and proportional testing.

## Selected design

Add one focused `src/core/task-session.mjs` contract module and reserve one
shared `capabilityState["task-session"]` slot in the existing version-4
`StateStore`.

The contract module owns exact shape, bounds, policy checks, safe relative
source references, and immutable model/session identity. `StateStore` owns
atomic persistence and the one-open-session rule. A later
`TaskSessionManager` will orchestrate routing, expiry, draft workspaces, and
business updates using this same contract.

Alternatives are rejected:

- embedding the validator in `StateStore` would mix generic persistence with
  Task Session semantics and make later manager tests harder;
- creating the full manager now would pull fourth-batch routing, workspace,
  expiry, and user-policy decisions into the first batch;
- increasing the state version would add migration and rollback risk without
  changing the existing version-4 envelope.

## Exact TaskSession contract

The stored object has exactly these fields:

```json
{
  "version": 1,
  "session_id": "program-generated UUID",
  "capability": "assistant-work",
  "status": "open",
  "model": "codex",
  "goal": "bounded current goal",
  "task_summary": "",
  "confirmed_requirements": [],
  "rejected_directions": [],
  "source_paths": [],
  "current_draft_version": 0,
  "recent_turns": [],
  "started_at": "2026-07-26T05:00:00.000Z",
  "updated_at": "2026-07-26T05:00:00.000Z"
}
```

Rules:

- `version` is exactly `1`;
- `session_id` is a canonical lowercase UUID generated by the program;
- `capability` must appear in an explicit runtime continuation policy;
- `model` must be allowed for that capability and never changes for the same
  `session_id`;
- status is one of `open`, `completed`, `cancelled`, or `expired`;
- goal is non-empty and at most 1,000 UTF-8 bytes;
- task summary may be empty and is at most 8,000 UTF-8 bytes;
- confirmed requirements and rejected directions contain at most 20 unique,
  non-empty strings, each at most 1,000 UTF-8 bytes;
- source paths contain at most 20 unique, non-empty relative POSIX paths, each
  at most 240 UTF-8 bytes, with no absolute path, URI scheme, backslash,
  tilde root, empty segment, `.` segment, or `..` segment;
- every stored source path must also be present in the caller-supplied verified
  source list;
- current draft version is an integer from 0 through 1,000,000;
- recent turns contain at most 12 `{role, text}` objects, role is `user` or
  `assistant`, text is non-empty and at most 2,000 UTF-8 bytes;
- the complete serialized session is at most 32 KiB;
- timestamps are canonical ISO strings and `updated_at` is not earlier than
  `started_at`;
- unknown fields, prototypes other than ordinary JSON objects, malformed
  values, and duplicate list items are rejected;
- validation always returns a deep clone and never modifies caller input.

## StateStore behavior

The state envelope remains version 4. Empty and migrated state gains:

```json
{
  "task-session": {
    "session": null
  }
}
```

`StateStore.open` accepts an explicit `taskSessionPolicy`. Existing state with
a non-null Task Session is validated against that policy before use. A missing
slot is normalized to `null` for backward compatibility.

The store exposes:

- `getTaskSession()` — returns a clone of the current open session, otherwise
  `null`;
- `saveTaskSession(session, {verifiedSourcePaths})` — creates the first open
  session, updates the same open session, or replaces a terminal session;
- `closeTaskSession(status, updatedAt)` — changes the current open session to
  `completed`, `cancelled`, or `expired`.

Only one slot exists. Saving a different `session_id` while another session is
open fails. Updating an existing open session must preserve capability, model,
started time, and never decrease draft version or updated time. Terminal
sessions cannot be updated or closed again. A later new session may replace a
terminal session.

Errors use bounded codes and never include session text, paths, identifiers, or
state content.

## Deliberate non-goals

This batch does not decide or implement:

- automatic expiry duration;
- draft retention duration;
- multiple, paused, or nested sessions;
- Router continuation preference;
- knowledge-ingest interruption behavior;
- workspace directory layout or file writes;
- source existence and allowed-root verification;
- recent-turn summarization algorithms;
- AssistantWorkDecision execution;
- outcome file sending.

Those require later R3 batches or owner directory/retention decisions.

## Tests and mutation targets

Use only synthetic data and temporary files.

- valid exact contract and deep cloning;
- every field bound, unknown field, unsafe path, unverified source, invalid
  timestamp, disallowed capability/model, and total-size rejection;
- StateStore version remains 4 and adds only one shared slot;
- service restart restores the same open session and draft version;
- a second open session is rejected;
- same-session updates preserve model and immutable identity and prevent
  version/time rollback;
- terminal status cannot continue or close twice;
- a new session can replace a terminal one;
- legacy version 1–4 state and existing daily-work/router/invoice behavior stay
  unchanged.

Development runs only Task Session and StateStore tests. The 337-test suite is
not repeated unless this local first-batch candidate is declared complete or a
cross-module failure makes it necessary.

## Deployment boundary

This contract remains on the local candidate branch. No GitHub push, merge,
production configuration migration, state change, service restart, real
message test, or Skill enablement occurs in this batch.
