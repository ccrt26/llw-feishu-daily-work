# V3.7.0 Minimal Knowledge Ingest Design

日期：2026-07-26
状态：已确认，进入实施
范围：V3.7.0 第二批；直接文字、TXT、Markdown、受管空目录、Knowledge Writer

## 1. 目标

在现有单一 Dispatcher、单一 Router 和静态 Capability Registry 中增加一个仍默认禁用的
`knowledge-ingest` 闭环。它处理一个明确的保存请求，将一个直接文字、TXT 或 Markdown
来源安全写成一个新的 Obsidian 知识项，或在受管资料根下创建用户明确指定的空目录。

本阶段不处理 Office、PDF、图片、飞书云文档、知识查询、连续写作和文件回传。

## 2. 已确认的资料根规则

生产私有配置提供至少两个不重叠的受管资料根：

- 工作资料根；
- 生活资料根。

公开组件配置只保存 `library_key`、安全显示名称、允许别名和绝对根目录。真实目录和别名
只存在于受保护的生产配置，不进入公开仓库、测试或普通日志。AI 只取得 key、显示名称、
别名以及受限枚举得到的相对目录段，不取得绝对根目录。

系统目录、Skills、维护文档、临时目录、每日工作、发票和其他未配置目录不属于知识根，
即使它们位于同一个 Vault 中也不得读取或写入。

## 3. 目录与确认规则

目录选择按以下顺序执行：

1. 用户明确指定一个允许资料根及相对子目录时，程序验证后使用该目录；缺失的空目录可直接创建。
2. 程序只枚举受管根下有界、无符号链接的相对目录段；Skill 根据用户请求和这份候选列表
   唯一选择已有目录。已有命名规则能够确定目标时，直接按规则执行。
3. Skill 建议新分类、存在多个可能目录、知识项标题不明确或命名规则无法唯一确定时，只提出一次确认。
4. 确认问题必须说明拟使用的资料根、相对子目录和命名规则；确认前不创建目录、不写文件。
5. 移动、重命名、合并、覆盖、删除、批量整理和受管根外操作始终拒绝。

一个分类目录可以先作为空目录创建。真实来源以后进入时仍按当次明确请求或已确认规则选择
该目录；系统不把未来任意附件静默绑定到以前创建的目录。

## 4. 知识项结构

每个新来源形成一个独立、可原子提交的知识项目录：

```text
<managed-root>/
  <confirmed-category-segments>/
    <normalized-title>/
      knowledge.md
      source.txt | source.md   # 仅在保留原件时
```

知识项标题来自通过严格 Schema 校验的 Skill 决策。程序负责规范化目录名；如果同名目录属于
不同来源，则追加来源哈希短后缀。AI 不返回绝对路径、最终目录名、冲突编号或覆盖指令。

`knowledge.md` 由程序根据经过校验的标题、摘要、标签、来源元数据和原文确定性生成。
直接文字只保存 Markdown；TXT/Markdown 是否保存原件由决策中的 `preserve_source` 控制。

## 5. 运行边界

处理顺序固定为：

```text
IncomingMessage
  → Router 选择唯一 knowledge-ingest
  → 准备一个直接文字或单个 TXT/Markdown 来源
  → knowledge.ingest（Codex-only）
  → 严格决策校验
  → 受管目录计划校验
  → Knowledge Writer 原子提交或返回 existing
  → 先保存 outcome
  → 原入口回复
```

Router 只获得文字或安全附件元信息。Skill 只获得用户请求、准备后的来源、允许资料库的
不透明 key 和安全显示别名，不获得绝对路径、平台标识、凭据、Vault 列表或其他资料。

## 6. Writer 与幂等

Knowledge Writer 必须：

- 验证 Vault 标志、受管根身份、owner、普通目录和无符号链接；
- 逐段验证 `folder_plan`，并确认最终路径仍在对应受管根内；
- 只创建空目录或一个全新的知识项目录；
- 根据 `library_key + source SHA-256` 派生稳定 `knowledge_id`；
- 同一资料根内的相同来源返回 `existing`；
- 同名不同来源不覆盖；
- 在同一文件系统内准备完整 staging 目录并原子发布；
- 写后复核普通文件、权限、哈希和固定文件清单；
- 失败时不留下半成品，不删除或修改既有资料。

直接文字原文不得进入状态和普通日志。Outcome 只保存状态、固定回复、相对工件路径和原入口
回复目标。

## 7. 配置与启用

配置版本继续使用尚未部署的 version 5，在其候选结构中增加默认禁用的
`knowledge-ingest` 配置：

- 私有 Skill 根；
- 私有临时目录；
- 受管资料根列表及安全显示别名；
- 最大来源字节数；
- AI 超时；
- 当前启用输入格式。

本阶段代码、测试和隔离闭环完成后仍保持：

- 私有 manifest 中 `knowledge-ingest.enabled=false`；
- 公开静态 allowlist 中 `enabled=false`；
- 正式配置不迁移；
- 生产不注册、不调用该 Capability。

## 8. 错误语义

错误分为：

- 需要确认：资料根、目录、标题或命名规则不唯一；
- 明确拒绝：无保存意图、格式不支持、多来源、修改既有资料或不安全目录计划；
- 技术失败：下载、来源检查、AI Schema、Vault、原子写入或写后复核失败；
- 已存在：同一受管资料根内的相同来源已完成入库。

任何失败都不尝试第二个 Capability，不泄露绝对路径、来源正文或内部错误。

## 9. 测试与验收

本阶段采用逐项 RED-GREEN-REFACTOR，定向覆盖：

- 直接文字提交、重复幂等和同名不同内容；
- 工作/生活两个受管根及安全别名选择；
- 用户明确目录直接创建；
- Skill 建议目录必须确认；
- 目标或命名不明确时零写入；
- TXT、Markdown 单文件准备和清理；
- 扩展名伪装、超限、符号链接、多附件和不支持格式；
- 路径逃逸、受管根外、移动、重命名、删除和覆盖拒绝；
- 原子提交、并发占位、失败无半成品和写后复核；
- 两个入口进入同一个 Capability 后得到同一业务结果；
- 未启用时现有 Router、每日工作、发票、PDFium、飞书和微信行为不变。

阶段完成时运行相关测试；只有进入最终集成门才运行一次完整组件回归。

## 10. 后续边界

Office 与飞书云文档属于下一阶段；`assistant-work`、知识查询、Task Session 和文件输出属于
后续独立阶段。本阶段不得为它们预建解析器、搜索服务、向量数据库或平台文件发送逻辑。
