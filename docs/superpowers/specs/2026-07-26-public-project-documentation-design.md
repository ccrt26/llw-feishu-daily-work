# 公开项目文档设计

日期：2026-07-26
状态：已由项目所有者批准
范围：为组件仓库与 Skills 仓库建立可供人和 AI 阅读的公开安全文档；不修改生产代码、配置、服务或业务数据

## 1. 目标

本次文档更新服务于两个直接目标：

1. 让不熟悉代码的人可以从仓库首页理解项目解决什么问题、当前已经做到什么、各组件如何协作。
2. 让 ChatGPT 等 AI 可以按稳定阅读顺序取得架构、职责边界、当前版本事实和后续设计接口，而不需要读取本机资料或猜测生产状态。

文档必须如实覆盖 V3.6.3 已完成的 PDFium 单处理器改动及正式验收结果，同时避免公开本机路径、平台身份、业务主体和真实票面数据。

## 2. 读者与阅读顺序

目标读者分为三类：

- 项目所有者：先读组件仓库根 `README.md`，了解当前能力和使用边界。
- 后续开发者：继续读 `docs/PROJECT_OVERVIEW.md` 和对应版本设计，理解组件职责、数据流、测试和变更原则。
- AI 评审者：按 README 中的“AI 阅读顺序”依次读取项目概览、V3.6.3 设计、两个仓库的 Skill 合同，再讨论后续功能。

根 README 不复制全部实现细节，只提供准确入口。细节应落在唯一负责该事实的文档中，避免多个位置长期漂移。

## 3. 文档结构

### 3.1 组件仓库

公开仓库：[llw-feishu-daily-work](https://github.com/ccrt26/llw-feishu-daily-work)

新增或更新以下文件：

1. `README.md`
   - 项目定位与当前稳定能力；
   - 飞书、微信共用核心链路的简化架构图；
   - 当前业务能力清单；
   - 安全与隐私原则；
   - 仓库导航和 AI 推荐阅读顺序；
   - 开发验证入口。

2. `docs/PROJECT_OVERVIEW.md`
   - 当前已实现架构与职责边界；
   - 消息、附件、路由、Capability、Skill、确定性规则和 writer 的完整关系；
   - 模型边界；
   - 配置、运行件和回滚原则；
   - 当前版本、测试和验收事实；
   - 明确列出尚未实现的范围和后续设计接口。

3. `docs/superpowers/specs/2026-07-26-pdfium-only-invoice-pdf-design.md`
   - 保留 V3.6.3 的技术设计和实施结果；

   - 将仅适用于本机的绝对路径改写为公开安全的逻辑位置；
   - 不改变既有技术决定或业务规则。

### 3.2 Skills 仓库

公开仓库：[llw-personal-ai-skills](https://github.com/ccrt26/llw-personal-ai-skills)

新增根 `README.md`，内容包括：

- 仓库用途及与运行组件仓库的关系；
- 当前 V3.6.3 运行基线集成的三个语义合同及其单一职责：
  - `feishu-intent-router`：只选择一个已启用业务能力；
  - `feishu-daily-work`：只处理每日工作记录语义；

- 输入输出 Schema、评测与模型支持的导航；
- 安全边界和 AI 推荐阅读顺序。

README 只总结合同，不复制每个 `SKILL.md` 的完整业务语义。具体语义继续由对应 Skill 作为唯一事实来源。

## 4. 公开安全边界

### 4.1 可以公开

- 项目目标、组件职责和调用顺序；
- 通用 Schema 名称和最小字段类别；
- 已启用能力及其边界；
- 模型支持原则；
- V3.6.3 使用单一 PDFium 处理器的技术决定；
- 测试总数、公开 Git 提交短哈希和脱敏验收结论；
- 固定资源限制、错误类别、回滚原则和开发命令；
- 使用虚构数据的示例。

### 4.2 不得新增到公开文档

- macOS 用户名、卷名、绝对路径或真实 Vault 目录；
- 公司名称、统一社会信用代码、银行信息或其他业务主体标识；
- 飞书、微信用户标识、会话标识、资源键或真实消息正文；
- 密钥、令牌、钥匙串内容、内部服务地址或受保护状态文件内容；
- 真实发票、票号、金额、日期、购买方、销售方或其截图；
- 可定位个人或生产资料的日志、备份路径和临时文件名。

公开文档可以说明“这些值存在于受保护配置或钥匙串”，但不能给出真实值或本机位置。

本次只治理新增和明确更新的文档，不宣称已经清理整个 Git 历史，也不以文档任务为由改写代码或历史提交。

## 5. 事实来源与防漂移规则

同一事实只指定一个主要来源：

| 事实 | 主要来源 | 其他文档的处理方式 |
|---|---|---|
| 项目入口和阅读顺序 | 组件 `README.md` | 只链接，不复制详细实现 |
| 当前架构、版本和验收状态 | `docs/PROJECT_OVERVIEW.md` | README 仅给简短摘要 |
| PDFium 设计、限制和实施证据 | V3.6.3 设计文档 | 项目概览引用该文档 |
| 每个业务 Skill 的精确语义 | 对应 `SKILL.md` | Skills README 只作目录和职责摘要 |
| 本机实时运行事实 | 私有系统事实基线 | 公开文档只记录已经确认且适合公开的快照 |

版本状态必须写明“截至日期”，避免把会变化的测试数或提交短哈希描述成永久常量。未来实现发生变化时，应先更新主要来源，再更新入口摘要。

## 6. 内容表达原则

- 先用人话说明结果，再给技术名词。
- 飞书和微信只画成两个入口；统一 Dispatcher 之后不得画成两套业务体系。
- 明确区分：
  - Skill：业务语义合同；
  - Capability：运行时执行单元；
  - AI 语义任务：读取或判断非确定性内容；
  - Node.js 确定性规则：根据已提取事实执行固定判断；
  - writer：只负责安全、幂等地写入目标。
- README 的图只表达稳定关系，不加入进程号、本机目录或部署瞬时状态。
- 对尚未实现的功能必须标记为“未实现”或“后续设计接口”，不得写成已有能力。

## 7. 验证

文档提交前必须完成：

1. 组件完整测试保持通过；
2. `git diff --check` 无格式错误；
3. README 中所有仓库内相对链接均指向存在的文件；
4. 跨仓库链接指向两个已确认的公开仓库；
5. 对新增和修改文档扫描本机绝对路径、密钥词、平台标识形态和真实业务主体；
6. 检查版本日期、测试数和提交短哈希与当前 Git 事实一致；
7. 人工按 README 给出的 AI 阅读顺序复读，确保不依赖本地 `SYSTEM_MAP.md` 也能理解；
8. 确认 Git diff 只有约定文档，没有生产代码、配置、锁文件或业务资料。

测试和扫描结果只能证明本次文档变更满足边界，不得表述为对整个历史仓库的隐私审计。

## 8. GitHub 同步策略

- 组件文档先在隔离分支完成、验证和提交，再合并到组件 `main` 并推送。
- Skills README 在独立文档分支完成并验证，再合并到 Skills `main` 并推送。
- 不把文档变更混入生产运行提交；是否同步到生产运行分支由分支一致性需要单独判断。
- 推送完成后报告两个仓库的分支、提交和可直接交给 ChatGPT 的阅读链接。

## 9. 完成标准

以下条件全部成立才算完成：

- 两个仓库首页都能独立说明各自用途；
- 组件 README 提供清晰架构、能力、边界和阅读导航；
- 项目概览准确记录当前 V3.6.3 状态；
- V3.6.3 设计包含本次单一 PDFium 调用链和正式验收结果，且不新增本机敏感信息；
- Skills README 准确说明三个当前集成 Skill 的职责、Schema、评测和模型支持入口，并区分其他已跟踪但未启用的 Skill；
- 测试、链接、格式、隐私边界和 Git diff 验证全部通过；
- 文档已进入两个仓库的 `main` 并同步 GitHub。
