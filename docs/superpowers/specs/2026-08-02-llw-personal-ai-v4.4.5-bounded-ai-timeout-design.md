# LLW Personal Assistant V4.4.5 十分钟主分析与自动分段设计

**状态：** 2026-08-02 项目所有者已批准设计方向，等待书面复核
**当前系统版本：** V4.4.3  
**前置状态：** V4.4.4 安全分类热修已部署；真实飞书云文档已通过导出和安全检查
**目标版本：** V4.4.5

## 1. 决策摘要

V4.4.5 不再把一个数字同时当作文档导出、AI 正常完成时间和系统故障上限，而是按职责设置独立边界：

| 边界 | 时间 | 到时行为 |
|---|---:|---|
| 飞书文档单次检查或导出 | 120 秒 | 终止该次只读外部操作，不能影响 AI 时限 |
| 整篇 AI 处理中提示 | 5 分钟 | 只发送一次“仍在处理中”，不终止 AI |
| 整篇 AI 分析 | 10 分钟 | 终止整篇分析，自动切换到分段模式，不能原样重试 |
| 单个分段或最终合并 | 5 分钟 | 该阶段失败，停止后续阶段并保持零写入 |
| 同一用户任务总处理 | 30 分钟 | 最终安全停止，保留来源并明确回复，不无限占用主链 |

因此，300 秒是用户可见的进度提示线，不是任务死亡线；600 秒才是一次整篇分析的硬上限。超过 600 秒后，程序必须改变处理方法，而不是继续增加整篇等待时间。

## 2. 已有证据与根因

真实飞书任务已经证明：

- 用户 OAuth 和飞书权限足够；
- 云文档可以导出为非空 DOCX；
- V4.4.4 已允许安全网页超链接，同时继续拒绝危险外部关系；
- 当前真实 DOCX 约 2.67 MB，正文约 6,673 个字符，含 14 个媒体对象；
- 来源准备成功后，Codex 在 120 秒触发 `assistant_timeout`；
- Writer 调用和知识库写入均为零，原来源仍在当前 Task Session。

这些证据只能证明“AI 需要超过 120 秒”，不能证明 300 秒一定足够。300 秒来自旧 invoker 的历史上限，不是对真实文档的实测完成时间。

第一次 V4.4.5 部署尝试还暴露了第二个根因：`main.mjs` 把 `personalAssistant.aiTimeoutMs` 同时传给 Codex、飞书文档导出器和附件下载器。候选配置从 120 秒改为 300 秒后，飞书导出器因自身合法上限仍为 120 秒而拒绝启动。生产已经按门禁完整回滚并恢复健康。

所以本版本必须先解除不同操作对同一个超时字段的错误共用，不能再用修改一个配置值的方式同时放大所有外部操作。

## 3. 目标与非目标

### 3.1 目标

1. 让当前保留的真实飞书 DOCX 能在合理时间内完成阅读、总结和一次确认入库。
2. 把用户无反馈等待控制在五分钟以内，把一次不透明的整篇分析控制在十分钟以内。
3. 整篇分析超过十分钟后，自动转为有界、只读的分段分析；不要求用户重新上传或发送“继续”。
4. 在任何超时、取消、分段失败或任务更新情况下，保持来源可恢复、Writer 零误写和 Outcome 顺序不变。

### 3.2 非目标

- 不增加 Agent、Router、Writer、长期服务、后台平台或第二条消息主链；
- 不扩大飞书/OAuth 权限、来源类型、文件大小或媒体数量；
- 不访问文档中的网页链接或其他外部关系；
- 不让部分结果直接写入知识库；
- 不提前实现 V4.5.0 的来源身份、版本关系和本地知识库读取；
- 不宣称十分钟内一定完成所有任务。十分钟是整篇处理上限，分段后的最终完成时间仍可能更长，但总计不得超过三十分钟。

## 4. 运行设计

### 4.1 独立时间预算

程序使用语义明确的独立预算，不再从 `personalAssistant.aiTimeoutMs` 派生文档取得时间：

- 飞书 `inspect`：每次最多 120 秒；
- 飞书 `export`：每次最多 120 秒；
- 飞书或微信附件下载：继续使用各自现有的安全上限；
- 整篇 Personal Assistant Codex：最多 600 秒；
- 每个分段分析：最多 300 秒；
- 最终合并决策：最多 300 秒；
- 从本轮正式分析开始到最终 Outcome：最多 1,800 秒。

`inspect` 和 `export` 是两个独立只读操作，因此来源准备的理论总耗时可以超过 120 秒；这不等于单个外部命令可以无限运行。

配置 Schema 继续为 7。正式 `personalAssistant.aiTimeoutMs` 使用 600,000 毫秒，旧 120,000 毫秒继续用于回滚兼容；300,000 毫秒不再作为整篇分析的正式值。五分钟提示和分段预算由运行合同命名，不复用为来源操作超时。

### 4.2 整篇分析阶段

现有入口、Task Session、来源准备、Codex 和 Writer 主链保持不变：

```text
飞书原消息
→ 已保留并通过安全检查的 DOCX
→ 一次整篇 Codex 分析
→ 十分钟内完成：现有 Writer/Outcome 流程
→ 十分钟未完成：取消本次 Codex，进入分段模式
```

本轮开始时继续发送现有“已收到，正在处理”。五分钟仍未完成时，使用独立幂等键只发送一次“文档仍在分析中，无需重新发送”。该提示不是完成 Outcome，也不授权 Writer。

十分钟到达时必须终止整篇 Codex 子进程。即使旧进程稍后产生文件或结果，任务 revision、控制器取消、Writer reservation 和提交前 current/compatible 检查也必须阻止其写入或回复。

### 4.3 自动分段模式

分段模式仍属于同一个 Personal Assistant 和同一个 Task Session，不建立新 Agent、队列或服务。它只处理已经通过安全检查并复制到私有任务工作区的 DOCX。

分段器以本地、确定性的方式读取 DOCX 包：

1. 按 Word 正文段落和标题边界提取文字；
2. 按关系和最近正文位置把安全内嵌图片归入相应段落；
3. 在现有上下文字节上限和模型图片上限内生成最多三个顺序分段；
4. 不解析或访问外部超链接、外部图片、模板、OLE、附件或未知关系；
5. 如果无法在三个合法分段内表达来源，则安全停止并说明需要缩小范围，不能静默遗漏内容。

进入分段模式时发送一次幂等进度消息。三个分段按顺序处理，同一时刻最多运行一个 Codex 调用。每个分段只允许返回结构化的只读观察结果，不提供任何副作用工具，也不能直接生成 Writer reservation。

每个分段结果必须包含：覆盖范围、核心事实、图片观察、未解决事项和来源位置提示。结果只保存在当前私有临时工作区，受现有任务总字节限制，不写入 Vault，不进入普通日志。

全部分段成功后，最后一次 Codex 调用只接收原始用户要求、受限分段结果和当前任务合同，生成一个现有 Personal Assistant 动作。只有这一次最终决策可以请求 `save_knowledge`，并继续经过现有工具校验、Writer reservation、任务兼容性复核、原子写入和 Outcome-before-reply 顺序。

从整篇分析开始计算，分段和最终合并合计不得超过三十分钟。每完成一个分段可以发送一条不包含文档内容的幂等进度消息。任务被用户更新、结束或取消时，立即取消剩余分段，所有部分结果作废。

### 4.4 不支持与失败行为

V4.4.5 的自动分段只针对当前已证实的安全 DOCX 路径。XLSX、PPTX、PDF、视频或多文件任务仍使用各自现有路径；若其整篇 AI 超时，保持来源和零写入，不假装已经分段完成。

以下任一情况都必须失败关闭：

- DOCX 分段准备无法证明完整覆盖；
- 超过三个合法分段；
- 任一分段或最终合并超时、退出异常或结果校验失败；
- 总处理时间到达三十分钟；
- Task revision 已变化或用户已取消任务；
- Writer reservation、current/compatible 复核或 Outcome 保存失败。

失败时清除临时分段结果，保留原始 Task Source；未获得最终、当前且合法的 `save_knowledge` 决策时，Writer 调用必须为零。回复应说明失败阶段、来源仍在、无需重新上传，并且不能建议原样重复整篇尝试。

## 5. 方案比较

### 方案 A：300 秒硬停止

改动最小，但把旧代码上限误当成真实完成依据；复杂任务在第 301 秒正常完成也会被错误杀死。拒绝。

### 方案 B：把整篇分析直接延长到 30 分钟

容易实现，但用户长时间看不到有效进展，故障进程也会长期占用唯一主链。拒绝。

### 方案 C：十分钟整篇上限，随后自动分段（采用）

符合用户等待耐心，有明确总资源上限，并让复杂任务通过改变方法而不是不断加时完成。代价是需要一个受限 DOCX 分段器、部分结果 Schema 和分段协调合同，但不改变入口、Agent、Writer 或长期服务架构。

## 6. 安全与幂等

- 分段器只接受已经通过现有 OOXML 安全检查的当前 Task Source；
- 安全网页超链接只作为文字保留，程序和模型都不得主动访问；
- 部分分析没有工具权限，不能产生任何知识库写入；
- 最终合并仍受“一轮最多一个工具调用”约束；
- 处理提示、切换分段和分段进度分别使用确定性幂等键；
- 新消息导致 revision 变化时，旧整篇分析、旧分段和旧合并结果全部失效；
- 日志只记录阶段、耗时、数量和错误码，不记录文档正文、标题、内容摘要、平台标识或 Vault 路径；
- 临时分段内容继续使用 owner-only 私有目录并在成功、失败或取消后清理。

## 7. 测试与真实验收

### 7.1 最小确定性合同

1. `main` composition 证明飞书导出固定使用 120 秒，Codex 单独使用 600 秒，附件下载不被 AI 配置放大。
2. 配置合同接受旧 120 秒和正式 600 秒，拒绝其他未批准值；其他能力的 AI 时限不变。
3. 五分钟只发送一次处理中提示，且不保存 Outcome、不调用 Writer。
4. 十分钟整篇超时后取消旧进程，只进入一次分段模式，绝不原样自动重试。
5. 分段器证明段落和安全内嵌图片完整且只归入一个分段，并继续拒绝危险外部关系。
6. 每个部分调用都没有副作用工具；只有最终合并可以产生一次 `save_knowledge`。
7. 任一分段失败、总时间到达三十分钟、任务 revision 更新或用户取消时，Writer 为零且来源保留。

### 7.2 纵向合同

新增一条覆盖以下链路的 DOCX 纵向测试：

```text
飞书云文档消息
→ 用户身份导出
→ V4.4.4 安全检查
→ 整篇分析模拟超过十分钟
→ 自动分为受限段
→ 只读部分结果
→ 最终 save_knowledge
→ KnowledgeWriter 一次原子写入
→ Outcome
→ 飞书一次最终回复
→ 临时分段清理
```

测试同时证明旧整篇结果、部分结果和进度消息都不能绕过 Writer 门禁。

### 7.3 真实验收

部署前建立并恢复验证 owner-only 回滚点。部署后先确认一个 LaunchAgent、一个 Node 主进程、一个直属飞书消费者、心跳推进、Skill 加载正常、原来源仍在且知识库未被提前写入。

项目所有者不需要重新上传，只发送“重试”。真实验收必须记录各阶段耗时和结果码但不记录内容：

- 若整篇分析在十分钟内完成，走现有一次入库路径；
- 若超过十分钟，必须自动进入分段路径并最终一次入库；
- 任一路径失败都必须证明来源保留和 Writer 零写入；
- 只有真实 Writer、Outcome 和原入口回复全部成功后，系统版本才更新为 V4.4.5。

## 9. 允许的实现边界

预计只涉及：

- Personal Assistant Codex 时间预算和取消控制；
- `main` 中来源操作与 AI 时间参数解耦；
- 当前 Task Session 内的 DOCX 分段准备、只读部分结果和最终合并协调；
- 幂等进度消息；
- 直接配置、invoker、分段器、协调器、Writer/Outcome 和纵向合同测试；
- V4.4.5 设计、计划、证据、报告和版本说明。

不得修改权限、Skill 业务语义、Writer 数据格式、知识库目录、用户资料、外部关系放行规则、模型、推理强度、服务数量或入口架构。
