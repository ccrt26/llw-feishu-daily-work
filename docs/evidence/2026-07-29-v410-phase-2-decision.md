# V4.1.0 第二阶段决策记录

## 为什么现在停止

第一阶段已经把与具体媒体后端无关的 Source Job、取消、恢复、流式接收、只读观察合同和会话续接基础建立好，并保持默认关闭。

但当前 LLW 生产组件调用的是后台 `codex exec`/只读工作区路径。2026-07-29 的官方 Codex manual 只明确给出文字与图片输入，没有音频或视频输入类型；一次不含私人内容的真实原始音频/视频门禁在 180 秒内也没有返回可验证答案。继续把媒体接入生产会变成“没有受支持读取后端，却宣称可以理解”，不符合可靠性要求。

## 不是在否定 Codex 的视频能力

Codex 桌面应用可以借助宿主环境、文件工具或未来的新接口处理视频。问题只在于：LLW 当前自动化组件使用的后台调用合同没有得到同等能力的官方确认。两个入口不能凭体验类推。

## 后续选择

推荐选择：允许一个最小本地媒体准备层。

- 只读取用户已经通过微信/飞书交给助手的媒体；
- 只做格式探测、解码、时间定位和必要的语音转写；
- 原始视频仍是主要来源，派生物明确标注为局部工作视图；
- 最终内容理解、任务判断和四个现有工具的选择仍全部由同一个 Codex Personal Assistant 完成；
- 不安装播放器界面，不引入外部视频理解模型，不启用站点下载器，不让模型任意执行 shell。

备选：等待 OpenAI 在 LLW 可调用的 Codex CLI/App Server 中正式提供并记录音频/视频输入合同。这样依赖最少，但上线时间无法确定。

不建议：接入第三方视频理解 API 或插件。用户已明确不需要，这也会增加隐私、费用和维护边界。

## 用户批准前的边界

- 音频、视频、普通 Web、B站和抖音仍不进入生产；
- 不修改生产配置和 Skill allowlist；
- 不安装 FFmpeg、Whisper 或其他依赖；
- 不部署、不申请权限、不提交、不推送。
