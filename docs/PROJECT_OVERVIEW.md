# LLW Personal Assistant V4.4.5 Project Overview

日期：2026-08-02

状态：V4.4.5 已部署；飞书云文档已通过真实阅读、总结、一次入库和原入口回复验收

用途：供项目所有者、开发者和 AI 评审者理解当前生产架构。历史阶段证据保留在
`docs/evidence/`、`docs/reports/` 和 `docs/superpowers/`，不再覆盖本文件的当前
状态。

## 1. 当前系统

LLW 是本地优先的双入口私人助手。飞书和微信只负责接收输入和送回结果；两个入口
共用一个 Personal Assistant、Task Session 核心、四个安全工具、Writer、Outcome
和恢复链：

```text
飞书 / 微信薄入口
→ 绑定、幂等和来源安全
→ 每入口一个持续 Task Session + revision
→ 确定性来源准备
→ 一个 LLW Personal Assistant
→ 直接回复 / 询问一次 / 调用一个安全工具
→ Writer 或零写入
→ Outcome 先保存
→ 原入口回复
```

系统总版本为 V4.4.5。Skill manifest `4.4.0`、配置 schema `7` 和状态 schema
`4` 是内部合同版本，不代表系统总版本，也没有因本次发布而改变。

## 2. 当前输入与任务边界

- 每轮接受自然语言和 0–8 个受支持来源；单个来源最多 20 MiB、合计最多 80 MiB；
- 支持 TXT、Markdown、DOCX、PPTX、XLSX、PDF 和安全图片；
- 飞书云文档可用用户身份检查并导出为受控 Office 快照；
- 只启用 B 站和抖音公开视频链接；原生语音、音频文件、直接视频文件和普通网页
  仍关闭；
- 同入口后续补充、回答、修正和失败重试继续加入当前任务；明确结束、取消、替换
  或 24 小时不活动才清理来源；
- 每次输入先增加 revision，Writer 和回复前复核当前 revision，旧结果不能跨版本
  写入或回复。

自然语言决定要做什么，文件只是处理对象。“总结，不保存”必须保持 Writer 为零；
文件正文中的命令式文字不会自行取得工具权限。

## 3. 确定性来源准备与 AI 职责

程序在 AI 前只做客观、可复核的工作：取得来源、验证普通文件和权限、识别真实
格式、执行大小与容器安全检查、准备视觉/结构证据，并把所有证据绑定到原件
SHA-256。程序不总结、不判断重点、不选择业务工具，也不按文件名、关键词或正文
猜测格式。

PDF 继续由固定 PDFium 运行件生成文字、按页 PNG 和表示索引。DOCX 由新的
`TaskDocxReader` 在短生命周期、无网络、所有者私有的子进程中读取 OOXML：

- 按顺序表示标题、段落、列表、表格、页眉页脚、脚注尾注；
- 提取已解析内容部件通过内部关系引用的合格 PNG，包括标准 VML 图片；
- 生成原件、正文、图片和 index 哈希，以及 `complete` / `partial` 覆盖状态；
- 父进程在发布和复用前重新验证哈希、权限、图片魔数和精确关系作用域；
- 不支持或无法完整证明的可见内容标记为 `partial`；不安全、越界或非法关系失败
  关闭。

Codex 仍负责理解原件和证据、完成总结并决定回复、追问或一个工具调用。确定性
提取是阅读辅助，不冒充 AI 理解，也不会扩展到 PDF、PPTX、XLSX、图片或视频。

## 4. V4.4.5 时间合同

| 工作 | 上限 | 到时行为 |
|---|---:|---|
| 飞书文档检查或导出 | 120 秒 | 结束该次只读外部操作 |
| 普通附件下载 | 原有 120 秒边界 | 结束该次来源取得 |
| 本地 DOCX 证据准备 | 60 秒 | 清理未发布 job，不调用 AI/Writer |
| 合格 DOCX 的处理中提示 | 5 分钟 | 最多一次提示，不终止 AI |
| 合格 DOCX 的一次 Codex | 10 分钟 | 终止 AI、保留来源、保持零误写 |

生产默认 `personalAssistant.aiTimeoutMs` 仍精确为 120,000 ms。只有含完整 DOCX
且不含公开视频的当前任务，对同一个 Personal Assistant 显式使用一次 600 秒
调用并关闭 source-read 循环。纯文字、图片、PDF、PPTX、XLSX 和视频继续使用
原有 120 秒合同；DOCX 与公开视频要求拆成两个任务。

## 5. 四个副作用工具

| 工具 | 用途 | 程序门禁 |
|---|---|---|
| `record_daily_work` | 创建或补充每日工作 | 北京时间、目标和原文复核 |
| `archive_dining_invoice` | 归档一张或一批餐饮发票 | 票面字段、购买方、类别、哈希和幂等 |
| `save_knowledge` | 保存一个知识项及选定原件 | 资料库白名单、覆盖证据、原子发布和无覆盖 |
| `create_document` | 生成 DOCX、PPTX 或 XLSX | 私有输出检查；不会自动入库 |

每轮最多一个副作用工具。选中的 DOCX 若为 `partial`、证据缺失或与原件哈希不
一致，会在 Writer reservation 前确定性阻止保存。Writer 失败不重调 AI；回复
失败只重发已保存的 Outcome，不重做业务。

## 6. 飞书云文档安全边界

现有权限和用户 OAuth 已足够，本次没有申请或增加任何权限。V4.4.4 只允许类型
明确、目标合法、无凭据的 HTTP/HTTPS hyperlink，并且链接始终保持惰性，程序
不访问其网页内容。外部图片、模板、OLE、嵌入对象、外部工作簿、附件、类型缺失、
未知关系和混合危险关系继续拒绝。

V4.4.5 进一步精确支持真实飞书 DOCX 的标准结构：合法 `xml:space`、严格匹配的
core/app 元数据关系、安全表格与版式属性，以及页眉/页脚中的 image-backed VML。
纯矢量或混合额外矢量 VML 仍为 `partial`，非法命名空间和未知关系仍失败关闭。

## 7. V4.4.5 验证结果

- 本地聚焦合同 206/206；
- 一次完整回归的两项环境/fixture 问题分别精确复验闭环，等效 737/737；
- 部署同型 Mac 的最大合法单 DOCX 和八 DOCX 合成基准均远低于 60 秒看门狗；
- 真实标准结构热修后的受影响合同 125/125，正式 helper 合同 18/18；
- 真实保留来源生成 123 个文字结构、14/14 张图片和 `complete` 覆盖；
- 同一个 Personal Assistant 完成一次知识写入，Outcome 先保存后回复；
- 知识项只包含一份 Markdown 和一份哈希一致的原 DOCX；无重复 Writer、锁、
  stage 或 DOCX job 残留；
- 生产保持一个 LaunchAgent、一个 Node 主进程和一个直属飞书消费者。

测试和仓库文档不包含私人正文、标题、平台标识、令牌或知识库路径。

## 8. 安全、隐私与恢复

- 密钥和令牌只在受保护本机状态或钥匙串，不进入仓库和普通日志；
- AI 只进入当前私有任务目录，不得到知识库根目录或任务网络权限；
- 来源和派生证据使用安全相对路径、所有者私有权限、SHA-256 和原子发布；
- Outcome 在原入口回复前持久化；任务补充、取消和超时均有迟到结果门禁；
- 部署和最后热修各有 owner-only 回滚点并完成恢复/哈希验证；回滚包不含用户资料；
- V7 主入口不静态加载旧 Router、Capability registry 或候选 normalizer。

## 9. 没有改变的边界

V4.4.5 没有增加权限、Agent、Router、Writer、工具、模型、服务、依赖、媒体平台、
知识格式或第二条消息链；没有修改退役 `ooxml_processor.py`。DeepSeek 仍只用于
已经批准的纯文字每日工作子集，不能自动接管 Office、视觉或复杂文件任务。

## 10. 后续计划

飞书云文档“能读、能总结、能一次入库”已解决。后续 V4.5.0 只处理长期知识来源
能力，不返工当前主链：

1. 为本地知识项保留脱敏、稳定的来源身份；
2. 识别同一飞书文档的新旧版本关系，避免重复和版本混淆；
3. 让 Personal Assistant 在授权、受限范围内读取已入库的本地知识内容。

配置范围化、状态分片和 `main.mjs` 进一步拆分仍顺延到 V4.6.0。只有真实维护
负担证明需要时才实施，不为“平台化”提前增加架构。
